## Defects found (real bugs) and fixes

All fixes are uncommitted. Each has a regression test that was mutation-checked (fails without the fix).

**B-1 (mobile, fixed): the supplier's tracking screen crashed on open.** `/supplier/tracking/:id` threw "useOutlet must be used inside an OutletProvider" because `TrackingScreenBody` called `useOutlet()` and the supplier routes have no `OutletProvider`. Repro: sign in as the supplier, open `/supplier/tracking/<any order id>`. Fix: `useOptionalOutlet()` in `contexts/OutletProvider.tsx`, used by `components/delivery/TrackingScreenBody.tsx`. Test: `tests/trackingSupplierNoOutlet.test.tsx` (renders the real provider-less tree; mutation: restoring `useOutlet()` fails it with the exact error).

**B-2 (mobile, fixed): a supplier delivering it themselves was shown as a Costonomy partner.** The API gives a `SUPPLIER_OWN` delivery row from the moment the order is ready (DRIVER_ASSIGNED, the store contact as "driver"). The tracker treated that as the partner phase: buyer saw "<Store> is heading to the supplier / Your order will be picked up shortly", a "Your delivery partner" card and an ON TIME tag; supplier saw "Partner on the way to you". The own-delivery copy ("Packed and ready ... delivering this themselves. No live tracking.", "Mark it delivered once it arrives.") never appeared. Repro: case 3. Fix: `partnerPhase` is false for own delivery in `lib/delivery/orderTracking.ts`. Tests: `tests/orderTracking.test.ts` (new describe block; the table test's `showPartner` expectation now says no partner for SUPPLIER_OWN). Mutation: reverting the one line fails 12 tests.

**B-3 (API, fixed): a drop beyond the 30 km radius poisoned the outbox relay for every event on the platform.** `DeliveryQuotingService.gather` saved the "UNSERVICEABLE: exceeds radius" quote without `provider_code` (NOT NULL). That insert ran inside the outbox drain's single transaction (`DeliveryDispatchListener` catches the exception but the transaction is already rollback-only), so `drain()` threw UnexpectedRollbackException every 2 s, the whole batch (payments, notifications, other tenants' events) stayed PENDING, and each retry re-hit unique keys on notification/realtime rows. Observed: events held 91 s, 205 s, 302 s and 15 minutes, released only when the drop became valid again; log: `Column 'provider_code' cannot be null ... insert into delivery_quote`. Repro: outlet more than 30 km from the store (the test moved outlet 1 to Mumbai), supplier marks the order ready. Fix: `RADIUS_LIMIT` as the provider code on that quote. Test: `DeliveryQuotingServiceTest.gather_exceeds30KmRadius_declinesWithoutQueryingProviders` now asserts `providerCode` not blank (mutation fails with "Expecting not blank but was: null"). See DECISION NEEDED D-3 for the wider hazard.

**B-4 (API, fixed): the no-partner retry and own-delivery offer used the database's local clock against UTC timestamps.** The native queries in `DeliveryRepository` compared UTC-stored `no_partner_since`/`last_retry_at` with `now(6)`. On a database not on UTC (this machine's MySQL is on IST, +5:30) every fresh delivery was outside its 30-minute retry window and immediately due for the own-delivery offer: auto retries never ran (`auto_retry_count` stayed 0) and the supplier was offered "I will deliver it myself" at once. Observed in case 6 before the fix. Fix: `utc_timestamp(6)` in all six places. Test: `DeliveryFlowIT$NoPartner.retryClockIsUtcWhateverTheDatabaseZone` (runs the queries on a +05:30 session; mutation fails with "a delivery that failed seconds ago is due for a retry ... was false"). API verification in a temporary worktree: `mvn -o verify -Dit.test=DeliveryFlowIT -Dtest=DeliveryQuotingServiceTest` gave 32 IT tests + 9 unit tests, 0 failures; the worktree was removed afterwards. The running dev server was then restarted once by `mvn -o -q compile` and cases 6 and 7 re-run green.

## DECISION NEEDED

**D-1 (behaviour): "Try again" after a rider cancels does not book a new rider straight away.** Case 8: partner cancelled -> DRIVER_CANCELLED; supplier "Try again" (`POST /deliveries/{id}/reassign`) answered 200 but the delivery went to QUOTE_FAILED with the same `provider_delivery_id`, because `reassign` excludes providers already tried and Pidge is the only real provider (the enabled MOCK_* providers do not quote against real routes). The automatic retry (nothing excluded) then booked a new Pidge order about a minute later and the case completed. Options: (a) leave it (self-heals, buyer sees "Still arranging delivery" meanwhile); (b) do not count a rider-level cancel as a provider failure, so Pidge stays eligible for the manual retry; (c) when every enabled provider is excluded, retry with none excluded (what the no-partner path already does).

**D-2 (money): cancelling a CONFIRMED credit order leaves the debt standing.** Case 12: restaurant `/cancel` and supplier `/supplier-cancel` on credit-funded orders cancel the order but `utilized` stays up (no RELEASE transaction; the order is already drawn and invoiced). This is the known open gap in DECISIONS D-091 ("credit's equivalent is a credit note and it does not exist yet"); the plan's expectation that exposure is reversed does not hold today. Options: issue a credit note/reverse the invoice on cancel before dispatch; or keep and surface it to ops. Side effect of this run: credit utilised on the test agreement rose from about 8,012 to about 42,500 of a 75,000 limit.

**D-3 (design): provider calls run inside the outbox relay transaction.** B-3 shows any exception from a listener (here `DeliveryDispatchListener`) marks the relay's one transaction rollback-only and stalls every event. Fixing the one cause is done; the structural options are: one transaction per event (or REQUIRES_NEW per listener), or dispatch deliveries off the relay thread.

## UI-DESIGN findings (copy and presentation, no change made)

1. Supplier no-partner panel contradicts itself: heading "Search finished" with "Still looking for a partner automatically until 1:59 AM. You can also try again now." (`PartnerSearchPanel` treats any retryable status as "stopped"). The plan expected an "x of 30 min" progress here; that only shows in the DELIVERY_REQUESTED/PROVIDER_SELECTED searching state.
2. "ON TIME" tag shows when Pidge states no ETA (commit 026a65a leaves it unstated): case 1 buyer reads "On the way ... ON TIME ... Step 4 of 5" with no time. The tag claims something the data does not say. The "Arriving in N mins" and late states were exercised by seeding `estimated_arrival_at`.
3. Late state shows both the "Running late / LATE BY 11 MIN" hero and an amber "Delayed" banner saying the same thing.
4. Pickup orders say "Delivering to <address>" and the buyer's ready state offers "Check in delivery" for a collection (case 4).
5. A delivery cancelled before pickup shows the supplier "Delivery cancelled / Request a delivery partner again" and the buyer "Still arranging delivery" (case 10): sensible, noted for the record.
6. Pidge cancelling an order that is already IN_TRANSIT is ignored by design (`DeliveryStatus.allowedTransitions`, doc 01 s13) and the delivery stays IN_TRANSIT: no screen change.
7. The supplier failure screen shows Pidge's raw reason ("Customer reject order - DRTO") as the subline (plan: reason visible to supplier; wording is the provider's).
